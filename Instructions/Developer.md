# Developer Agent Instructions

Use this role when implementing backend, frontend, or shared application behavior for InsightPilot.

## Project Shape

- Backend: Go module `insightpilot`.
- Backend entrypoint: `cmd/server/main.go`.
- Backend HTTP handlers: `internal/api/handler.go`.
- Data parsing/profiling/aggregation: `internal/data/`.
- Frontend: Next.js app under `frontend/`.
- Sample datasets: `samples/`.
- Do not recreate the removed root Node backend files. The root app is Go now. Node belongs to `frontend/` only.

## Local Commands

Run backend:

```bash
go run ./cmd/server
```

Run backend on another port:

```bash
PORT=3001 go run ./cmd/server
```

Test backend:

```bash
mkdir -p .cache/go-build && GOCACHE=$PWD/.cache/go-build go test ./cmd/server ./internal/...
```

Build backend binary:

```bash
mkdir -p .cache/go-build && GOCACHE=$PWD/.cache/go-build go build -o server_bin ./cmd/server
```

Run frontend:

```bash
cd frontend
npm run dev
```

## Engineering Rules

- Prefer small, explicit Go functions over large agent-style blobs.
- Keep deterministic data processing in `internal/data`.
- Keep HTTP/request/response behavior in `internal/api`.
- Keep long-running agent orchestration behind interfaces so it can be tested without calling external services.
- Do not put secrets in source files. Use environment variables.
- Do not add root `package.json`, root `node_modules`, or root Jest tests unless the project intentionally reintroduces a Node backend.
- Preserve API compatibility where possible:
  - `GET /api/health`
  - `GET /api/datasets`
  - `POST /api/upload`
  - `POST /api/analyze`
  - `POST /api/connect-source`
  - `GET /api/export/cleaned-csv`
  - `GET /api/pinned-charts`
  - `POST /api/pin-chart`

## Agentic AI Development Direction

The current analyzer is deterministic. Future agentic AI work should evolve it in layers:

1. Add an `Analyzer` interface in Go.
2. Keep the current deterministic analyzer as a fallback implementation.
3. Add an LLM-backed analyzer behind the same interface.
4. Give the LLM structured tools instead of letting it directly invent responses.
5. Validate all generated SQL, chart specs, and recommendations before returning them to the UI.

Suggested internal shape:

```text
internal/agent/
  analyzer.go        # Analyzer interface and request/response structs
  deterministic.go   # current local logic moved behind the interface
  llm.go             # provider-backed implementation
  tools.go           # allowed tools such as profile lookup, aggregation, SQL validation
  guardrails.go      # validation and safety checks
```

## Agentic Safety Rules

- Treat uploaded data and user prompts as untrusted input.
- Never execute arbitrary code generated by an LLM.
- Never allow the LLM to access files outside the intended dataset context.
- Never expose environment variables, API keys, stack traces, or local file paths in user-facing responses.
- Require structured JSON from LLM calls and validate it before use.
- If SQL support is added, use allowlisted read-only SQL and parameterized execution.
- Keep every agent step auditable: input, selected tool, tool result summary, final answer.

## Data Behavior Expectations

- `YYYY-MM`, `YYYY/MM`, `YYYY-MM-DD`, and `YYYY/MM/DD` should profile as date-like values.
- Trend charts should use date columns.
- Segment charts should prefer business categories such as `segment`, `category`, `region`, `product`, `department`, or `channel`.
- Metric selection should use the prompt when possible, then fall back to the first numeric column.
- Empty list responses should encode as `[]`, not `null`, where the frontend expects arrays.

## When Changing APIs

- Update backend tests in `internal/api`.
- Update frontend API calls in `frontend/src/app/page.tsx` if response shapes change.
- Update `README.md` and `frontend/README.md`.
- Rebuild `server_bin` if the checked-in binary is still part of the workflow.
